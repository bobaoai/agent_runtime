# Chinese Writing Voice（中文写作守则）

## 元数据

- **类型**: BestPractice
- **适用场景**: 用中文写任何会被读者带走判断的产物 — design doc / 报告 / 邮件 / 推文 / 文章 / slide speaker notes / 长 response。读者是技术人 / Builder / 同事 / 自己
- **创建日期**: 2026-04-25
- **来源**: 内化自 [`grapeot/context-infrastructure`](https://github.com/grapeot/context-infrastructure) 的 `rules/COMMUNICATION.md`（grapeot 长期高产中文技术写作的反模式提炼），与 Hoveath 自家 `bestpractice_prose_without_editorial_meta.md` 形成两侧夹击：本 skill 管"中文 voice 不像 AI 翻译"，prose-without-editorial-meta 管"写关于世界不写关于稿件"

---

## 核心原则

**让事实自己说话，不让形容词代替论证。**

中文写作里的 "AI 味" 不是某一句话特别假，而是七层细节的累积：句式压缩、滥用比喻、铺元评论、英文直译、缺承接、链接抽象、技术名裸写。每层都微小，叠在一起读者立刻能闻出来。

本 skill 把这七层各自的反模式 + 改写示范固化下来，让交付前能扫一遍快速消除。

## 1. 句子层面

### 1.1 否定改正向

与其说 X 不是 Y，不如直接说 X 是什么。中英文都适用，slide / speaker notes 严格执行。

| 原文 | 改写 |
|---|---|
| `it doesn't know your config` | `it goes in blind: config unknown` |
| `this isn't just faster` | `this is a categorical shift` |
| `not just coding` | `brainstorming, drafting, planning, everything` |
| `it's not a generic AI` | `it graduates from generic AI to your AI` |
| `you're not a user of the tool` | `you end up serving as a component of the tool` |

### 1.2 禁「很 + 形容词 + 冒号」做句首引出解释

「实验设计很直接：」「结果很清晰：」「原因很简单：」是典型 AI 句式。问题：用一个形容词跳过论证责任。人类写作让事实自己说话，或用更精确的动词名词承接。

| AI 味 | 改写一（事实承接） | 改写二（直接陈述） |
|---|---|---|
| 实验设计很直接：他们只对比了 SFT 和 RL 两组 | 他们只对比了 SFT 和 RL 两组，实验设计上做了极简处理 | 他们只对比了 SFT 和 RL 两组 |
| 结果很清晰：RL 模型正向迁移 3.5-11% | RL 模型在 OOD 上正向迁移 3.5-11% | 同左 |

不是所有「很」都不行。「这听起来很基础，但确实是需要学的」自然，因为在设置预期落差，有信息增量。判断标准：「很」后面是不是判断总结。是 → 删；不是 → 保留。

### 1.3 禁单字收尾压缩

「域名往上追」「年份近」「机构真」「格式齐」读起来像电报。改成「顺着域名追踪」「年份较近」「机构真实」「格式齐整」。

判断标准：去掉上下文后这个单字还能不能独立成义。能（"这件事本身很小"里的"小"）→ 保留；不能 → 展开。

### 1.4 禁笼统方向词

「往反方向走」「往坏的方向发展」「正在往另一个方向演进」让读者猜具体是什么。直接写具体变化。

| 笼统 | 具体 |
|---|---|
| 模型往反方向走 | 模型确实在引用来源了，但那些来源本身就是假的 |
| 项目往坏方向发展 | 上周三次部署都因为 schema 不一致回滚 |

### 1.5 句子尽量平直

能拆两句拆两句；能用冒号或分句的不用破折号（——/—/--）做情绪性停顿；不用引号包裹概念词（除非真有歧义）。

## 2. 修辞与比喻

### 2.1 禁用清单（口语化 / 战争 / 身体感比喻）

直接写它如何演化、问题在哪、差异在哪个维度。禁词：

| 禁词 | 真正想表达的 |
|---|---|
| **长出来 / 长出了**（用于系统抽象事物） | 逐步发展 / 逐步形成 / 演化为 |
| **很硬 / 很锋利** | 边界明确 / 判断锐利 / 论证扎实 |
| **收口** | 收尾 / 闭环 / 落地 |
| **很稳 / 更稳** | 鲁棒 / 一致性更好 / 误差更小 |
| **击穿** | 否定了这个预设 / 这个假设不成立 |
| **拆解** | 分析 / 分成几层看 / 逐项检查 |
| **闭眼编** | 没有检索就生成 / 缺乏 grounding |
| **结构性**（结构性原因/矛盾） | 直接写具体机制、约束来源、冲突位置 |
| **崩 / 撑不住 / 撑不起**（笼统状态） | 异常终止 / 请求失败 / 会话漂移 / 输出质量下降 / 缓存失效 / 前提不成立 / 难以维持 / 各方不再对齐 / 一致性掉队 |

仅在明确指宕机 / 进程崩溃时保留「崩」。

注意：中文里**自然的拟人化**（如「模型学会撒谎」「算法很聪明」）不在禁词内，不要矫枉过正。

### 2.2 比喻滥用症状

某个比喻被自己滥用时（每个反驳都「击穿」、每次分析都「拆解」），它就失去了具体含义。回到要表达的本意，用更精确的动词名词。

## 3. 元评论（占比应接近零）

### 3.1 禁用元评论代替论证

元评论 = 标注自己正在做什么。不是论证。读者能从内容看出你在做什么。

具体症状：

- 标题或段首用「这篇文章回答什么 / 一个更一般的判断 / 回到 X 场景」代替直接进入内容
- 用「这个框架」「这种说法」指代前文后做评价，而不是直接给出自己的判断
- 「不是 X 而是 Y」句式在全文反复出现作为论证框架（偶尔强调一次没事，反复就是模板）

如果有必要做路标，一句话带过，不独占一段。

### 3.2 例子

**AI 味**：
> 这篇文章回答的是 RL 是否真的提升泛化能力。
>
> 一个更一般的判断是：泛化能力跟训练范式不是简单的因果关系。

**改写**：
> RL 在 OOD 上正向迁移 3.5-11%，但 SFT 在同一组任务上回退 8.2%。这个落差不是范式选择本身造成的，是训练数据分布不同导致的。

## 4. 译文体（中文不是英文的逐句翻译）

### 4.1 典型硬译

| 英文 | 硬译（错） | 中文化（对） |
|---|---|---|
| stand on a layer | 站在某一层 | 属于哪一层 |
| serves X | 服务的是 X | 针对的是 X |
| the evidence for X is clearer | X 的证据更直接 | 换到 X 上看更清楚 |
| black box / black-box term | 黑盒词 / 黑盒子 | 这个词很模糊 |
| blast radius | 爆炸半径 | 判断半径 / 影响范围 / 具体功能描述 |
| 解耦（在组织/管理语境） | 解耦 | 分开 / 拆开 |
| uncomfortable / unsettling | 让人不舒服 / 让人不安 | 跟主流预期相反 / 违反直觉 / 具体说明哪里不对劲 |

「解耦」在工程上下文 OK，在组织 / 管理语境直接说「分开」。

### 4.2 抽象名词作主语 + 「比 X 更 + 形容词」

幻灯片标题感强，是同一类毛病。

**硬译**：
> 加载由每个人的 INDEX 文件控制。

**中文化**：
> 加载这件事，由每个人的 INDEX 文件控制。

加一个「这件事」把抽象动词名词化的主语接住。

### 4.3 自检方式

写完读一遍。若语序、隐喻、动词搭配像刚从英文逐句翻过来 → 按原意改成中文里自然的主谓结构和常用搭配。

专有名词、API、协议名、必要的技术英文保留。

## 5. 承接词与节奏（中文是话题驱动）

### 5.1 底层差异

- **英文**：主语驱动，每句 who does what 写明白；句间靠代词和 connective（however, therefore, because）保持连贯，connective 自身带信息量
- **中文**：话题驱动，主语经常省略；句间连贯靠虚词维持

把英文直译过来时，译者把英文 connective 全翻出来（「然而」「因此」），同时省略掉英文里没有、中文需要的轻承接 — 因为原文里没对应的词。结果：译文全是重承接、没有轻承接，读起来咚咚咚全是重拍没有弱拍。

这是翻译腔最隐蔽的一类，因为它是「缺了什么」而不是「多了什么」，校对时不容易抓。

### 5.2 轻承接清单

| 类别 | 承接词 |
|---|---|
| **起句承接** | 这样做、这样一来、这里、这套东西、这件事、这套机制背后 |
| **轻转折** | 不过、话说回来、至于、反过来看、换句话说 |
| **话题切换** | 再往上看一层、回到开头那个矛盾、说到底、真正想说的是 |
| **对照标记** | 代价是、好处是、麻烦在于、关键是、不一样的地方在于 |
| **语气词** | 呢、吧、嘛（独立成段问句尾部加「呢」字，避免审讯感） |

### 5.3 判断标准

把一段写完之后**出声念一遍**（不是心读）。如果节奏像在念条目清单、没有呼吸感 → 大概率承接词被省掉了。

不是每句都加。段内主谓结构已经在走的地方不必强塞。**默认做到「每段开头一个轻承接」**，段中间已顺的不再加。

### 5.4 分寸

承接词太密会显得啰嗦、像日常口语博客。当一段里连续三四句都没任何承接 → 检查。

---

## 6. 链接文字承载信息

不要用「前作」「这里」「之前讨论过的」「这篇文章」做 link text。英文博客 `see [previous post](...)`、`as discussed [here](...)` 在英文 OK 因为读者有悬停预览习惯，中文搬过来读起来脱节。

Link text 应承载**具体信息**：文章名 / 功能名 / 具体名词短语。

| 抽象（错） | 承载信息（对） |
|---|---|
| 这篇文章的[前作](/...) | 这篇文章的前作 [Context Infrastructure](/...) |
| 参考[这个 skill](/...) | 参考 [share_report skill](/...) |
| 详情见[这里](/...) | 详情见 [bestpractice_doc_self_review](/...) |

读者没点进链接之前就应该知道这是什么。

## 7. 代码标识符与例子选择

### 7.1 反引号包技术名

技术标识符（表名、字段名、API 名、配置项、文件名）必须用反引号，哪怕在中文段落里。裸写 `orders`、`user_id`、`TAVILY_API_KEY` 之类，读者不确定是专有名词还是笔误。反引号 = 「这是技术标识符」的视觉信号。

### 7.2 例子选择贴近读者心智

不要为了显得专业用 `fct_orders` / `dim_users` 这类 dbt 命名规范 — `fct/dim` 前缀只对数据工程师熟悉，对 PM、manager、非数据背景工程师都是障碍。`orders` / `users` 这种裸名所有人都认识。

专业命名留给真的在讨论专业话题的地方。

## 8. 整体层面

不用华丽辞藻，不用「惊喜」这类营销词汇，不用「值得认真对待 / 值得深思 / 值得关注」这类居高临下的推荐语。直接写出它为什么重要、影响了什么判断。

不说废话，不说客套话，直奔主题。用数据和逻辑说话，不靠形容词。不滥用 bullet points，**尽量用自然语言段落表达**（bullet 适合列表，不适合论证）。

## 9. 自查 checklist（交付前出声念一遍 + 扫这 8 项）

- [ ] 没有「不是 X 而是 Y」反复出现做论证模板
- [ ] 没有「很 + 形容词 + 冒号」句首
- [ ] 没有单字压缩收尾（域名追、年份近、格式齐）
- [ ] 没有笼统方向词（往反方向、往坏方向、往另一个方向）
- [ ] 没有 §2.1 禁词清单里的口语化战争比喻
- [ ] 没有元评论代替论证（「这篇文章回答 X」「一个更一般的判断」独占段）
- [ ] 没有英文逐句直译痕迹（stand on / serves / blast radius / black box）
- [ ] 链接文字承载具体信息（不是「前作 / 这里 / 这个 skill」）
- [ ] 技术标识符用反引号
- [ ] 出声念一遍：每段开头有轻承接，节奏不像念条目

任何 [ ] 没勾，回去改。

## 11. 不适用范围

- **临时 changelog / handoff note / commit message / scratch**：editorial meta 是它们本职，本 skill 只在交付给读者的产物上严格执行
- **代码注释**：保留极简，注释不是文章
- **非中文产物**：英文写作时大部分原则的中文版本不适用，但 §1.1 否定→正向跨语言通用，§3 元评论 / §6 链接文字 也跨语言适用
- **slide bullet 列表本身**：bullet 形式本来就压缩，不必要求承接词节奏
