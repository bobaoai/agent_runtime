# A17. 五面墙：可靠性链条同步失效

## 1. 核心公理

Agent 不是在某一个点出问题，而是让传统软件可靠性保障链条上的五个环节（防错 / 观测 / 状态管理 / 验证 / 治理）的底层假设同时失效。这五个环节都默认"被管理对象的行为是确定性的"，agent 的概率性输出一次性打破了这个共同假设。在引入 agent 时，要把"可靠性"看作一条同时漏水的五段管线，而不是某个单点缺陷。

## 2. 深度推演

### 2.1 五面墙的统一根因

| 环节 | 传统假设 | 被 agent 打破后表现 |
|---|---|---|
| 防错 | 错误模式可穷举，逐组件加 guard 即可 | 多 agent 串联时，每个 guard 都通过，组合产出虚构高置信度结论 |
| 观测 | 被观测对象是结构化数据，可设阈值 | 自然语言 / 数据语义产出无现成度量，漂移静默发生 |
| 状态管理 | 被管理对象不感知资源约束 | Agent 感知 context window 余量并主动走捷径（context anxiety） |
| 验证 | 同输入 → 同输出，pass 一次代表以后也 pass | 输出概率性，今天 pass 的 case 明天 fail |
| 治理 | 被授权做某事就只做那件事，每次方式相同 | 同权限 / 同输入下 agent 可能做出授权范围外的操作 |

五个环节的失效根因是同一个：底层假设建立在确定性系统上。这意味着不可能用"再加一道单点防御"来解决，必须重做这五段中的至少几段。

### 2.2 这不是模型问题，是基础设施问题

五面墙不属于模型能力范畴（不能等下一代模型修复它们），也不属于 prompt / context engineering（后者关注模型输入质量）。它们是 infrastructure 缺口：agent 的能力跑在了基础设施前面。把希望寄托在"换个更强的模型"上，会绕过实际要解决的工程问题。

### 2.3 五面墙在不同领域形状不同

通用领域、data infra、coding agent、ops agent、payment agent，撞的是同一组五面墙，但每面墙的具体形状不同。例如 data infra 里：
- 防错的"组合爆炸"表现为静默的语义错误（日期格式漂移、join 出空集）
- 观测从"管线跑通没"变成"数据有没有变味"
- 状态管理从代码 lineage 变成数据 lineage 的概率化
- 验证面对的是数据正确性定义本身的模糊
- 治理面对的是 identity explosion（见 A20 候选 / V05）

诊断时先确认"哪几面墙在你的场景里最显形"，再选对应的工程实践，而不是套通用清单。

### 2.4 旧管理学是它的原则祖先，但不是工程实现

五面墙在管理学里都有对应物（跨部门组合性风险、KPI 失效、员工感知压力走捷径、产出波动需要持续追踪、组织扩张管控失灵）。原则相通，但 agent runtime 的约束（概率性输出、context window、工具调用不确定性、多 agent 状态同步）要求一套全新的工程实现。Harness engineering 这个词流行起来，本质是给"在 agent runtime 里重新实现旧管理原则"这件事一个能被定价、能被讨论的名字。

## 3. 应用判定

### 何时使用

- 评估一个 agent 系统是否生产 ready 时
- 复盘一次 agent 事故时，判断这是局部 bug 还是链条性失效
- 设计新 agent 工作流前，预判哪几面墙最容易先漏水
- 听到"再换个更强的模型就好了"这类说法时，用来反驳

### 如何实践

1. 把当前 agent 工作流按五个环节做一次切片：防错 / 观测 / 状态 / 验证 / 治理。
2. 对每个环节问：底层假设是不是"行为确定"？现在有没有被概率性输出打破？
3. 找出最先漏水的那 1-2 段，先补这两段，而不是全面改造。
4. 补的方式优先选"环境层 / 结构层"修复（如限制并发上下文、加 staging、加 workflow agent 强制顺序），其次才是 prompt 层。
5. 沉淀：这次撞到的是哪面墙，邻近场景里还会不会再撞，能不能升级成 portable lesson。

## 5. 简化准则

每次接手或评估一个 agent 系统时，至少问自己五件事：

1. 防错：单点都过的情况下，组合输出会不会变成虚构高置信度结论。
2. 观测：自然语言或数据的语义漂移有没有度量手段。
3. 状态管理：agent 是否会感知到资源约束并改变行为。
4. 验证：是否还在用 pass/fail，而不是基于评判标准的统计评估。
5. 治理：agent 的实际行为面，是否超出了它被授权的行为面。
