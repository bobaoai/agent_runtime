# A19. 概率性面积最小化

## 1. 核心公理

在多步骤 agent 系统里，把 LLM 调用限制在真正需要语义判断或开放推理的步骤；其余步骤——顺序控制、格式清洗、语法校验、权限检查、字段映射、数据格式转换——一律用确定性代码或 workflow agent 实现。"用 LLM 做能用代码做的事"是反模式。系统的可靠性约等于其概率性步骤数目的反比例函数：每减少一个本可由代码处理的 LLM 调用，错误组合空间就缩小一个量级。

## 2. 深度推演

### 2.1 概率性步骤是误差源，不是中性步骤

每一次 LLM 调用都引入一个非零的偏差概率（输出格式漂移、自我审查偏移、幻觉、漏指令）。多个 LLM 步骤串联时，总体可靠性是每步可靠性的乘积，下降速度比直觉中的"线性叠加"要快得多。三个 95% 的 agent 串联只剩 86%，五个 95% 串联只剩 77%。把不必要的 LLM 调用替换成代码，等于把 100% 可靠的步骤换进乘积里。

### 2.2 哪些步骤不需要 LLM

可以用代码替代 LLM 的常见步骤：
- **顺序控制**：哪个 agent 先跑、哪个后跑、何时进入循环、何时退出 → workflow agent / state machine。
- **格式清洗**：去掉 markdown 代码围栏、补分号、统一引号 → 正则 / AST。
- **语法 / 结构校验**：SQL 是否合法、JSON 是否符合 schema、代码是否能编译 → sqlglot / pydantic / 编译器。
- **权限 / 边界检查**：是否访问了禁止的表、是否调用了未授权的 API → 静态分析 / RBAC 中间层。
- **字段映射 / 简单变换**：字段重命名、单位换算、ID 解析 → 配置表 / 函数。
- **去重 / 排序 / 过滤**：本质是确定性数据操作 → 数据库 / pandas。

凡是输入空间有限、规则可枚举、输出可校验的步骤，都不应该交给 LLM。

### 2.3 什么时候必须用 LLM

LLM 的真正用武之地是输入空间开放、规则不能枚举、需要语义压缩或语义生成的步骤：
- 自然语言理解意图
- 跨域类比、归纳、推理
- 摘要、改写、翻译、风格迁移
- 在没有标准答案时给出候选
- 解释 / 说明 / 沟通

把这类步骤识别出来，单独保护，是提升整体可靠性的核心动作。

### 2.4 Workflow agent 把 best practice 编码进结构

Google Cloud 的 ADK 案例里，"先取 schema 再生成 SQL 再校验"这条 best practice 不是写在 prompt 里"请你按顺序做"，而是用 SequentialAgent 把这个顺序编码成不可绕过的结构。这是 A19 的标准范式：用结构性约束代替 prompt 性约束。Prompt 性约束是一句建议，agent 可以忽略；结构性约束是边的拓扑，agent 没有选择。

### 2.5 它的反命题：把所有事都丢给一个 super-prompt

常见反模式是相信"模型够强了，写一个长 prompt 让它一步到位"。这种做法不仅可靠性低（所有步骤的概率性误差累积在一次调用里），也很难调试（哪一步出了错无法局部定位），还很难维护（修一个步骤要改整段 prompt）。A19 的对立面是 mono-prompt-ism。

### 2.6 它和 A11 是对偶关系

A11 讲"工具组合带来非线性能力扩展"，A19 讲"组件类型分工带来非线性可靠性提升"。一个讲扩展，一个讲约束。两者合起来描述了 agent 系统设计的两个正交维度：宽度（工具数量）和纯度（每种工具用在该用的地方）。

## 3. 应用判定

### 何时使用

- 设计任何超过 2 步的 agent 工作流时
- Debug 一个不稳定的 agent 链路时（先问：这条链路里有几个 LLM 调用是必须的）
- 评审他人的 agent 架构时
- 当你正打算往 prompt 里加一句"请你按以下顺序…"时——这是该改成结构性约束的信号
- 当一个 LLM 调用反复在同一类小问题上出错时——通常意味着这一步本来就不该是 LLM 调用

### 如何实践

1. 把 agent 工作流画成节点 + 边。
2. 给每个节点打标签：是"语义步骤"还是"机械步骤"。
3. 所有机械步骤替换成代码 / workflow agent / 静态校验工具。
4. 所有 best practice（先取 schema、先校验再执行、先 dry-run 再写入）从 prompt 里搬到边的拓扑上。
5. 计算改造后剩余 LLM 节点数。如果还能合并或剥离，继续做。
6. 在每个剩下的 LLM 节点旁边，配一个确定性的"批评者"或"校验者"，形成 generate-and-critique 局部回路。

## 4. 相关公理

- **A11 工具组合即能力扩展**：宽度 vs 纯度的对偶。
- **A04 可靠性是管理问题**：A19 是"可靠性管理三角"中"流程容错设计"维度的具体设计原则。
- **T07 隔离-处理-验证闭环**：A19 是 T07 在 agent 拓扑层的展开。
- **T02 结果确定性**：把"完成"的判定做成确定性边，而不是 LLM 自我宣称。
- **A14 prompt 边界卫生**：把约束从 prompt 搬到结构里，本质是更进一步的边界卫生。

## 5. 简化准则

接手或设计任何 agent 系统时，至少问三件事：

1. 这条链路里到底有几个 LLM 调用是必须的，能不能再砍一个。
2. 哪些 best practice 现在还写在 prompt 里，能不能搬到结构上。
3. 每个 LLM 节点旁边，有没有一个确定性的校验者兜底。
