# A14. Prompt 边界卫生

## 1. 核心公理

下游 prompt 只应携带会改变下游输出质量的信息。上游 orchestration、persona 来源、包装保证、内部控制理由属于 control-plane，应留在上游。写给执行者或 writer 的 task-plane prompt 只保留任务目标、事实边界、风格约束、判断要求、输出格式。

## 2. 深度推演

### 2.1 信息密度比信息总量更重要

很多 prompt 失败，不是因为信息太少，而是因为信息层级混乱。模型看到的每一句话都会竞争注意力。如果 prompt 里混入了对下游无用的控制信息，真正关键的任务指令就会被稀释。结果不是模型彻底误解，而是输出变钝：更啰嗦，更像复述，更少判断。

### 2.2 control-plane 与 task-plane 是两种不同语言

control-plane 处理的是系统如何组装、为什么这样路由、哪些边界已经由上游保证、persona 从哪里对齐。这些信息服务于管理者、编排层、规则层。task-plane 处理的是执行者现在要产出什么，以及什么算好。把两层混在一起，相当于让执行者一边做事，一边听系统设计说明。多数情况下，这不会提高质量，只会制造 meta noise。

### 2.3 低价值 guardrail 会挤占高价值 judgment

当 prompt 容量有限时，最该留下的是能直接改变结果的指令：事实边界、证据使用方式、风格约束、必须给出的判断、明确的输出结构。像 persona 标签、包装保证、调用方已经保证的隔离条件，这些属于低价值 guardrail。它们会挤占真正重要的注意力预算。

### 2.4 管理者的责任是分层，不是倾倒上下文

好的 AI 管理不是把所有知道的东西一股脑喂给下游，而是决定每一层各自该知道什么。上游负责保留系统理由、控制逻辑和失败保护。下游负责在一个干净的任务面内做高质量产出。这个分层本身就是管理能力的一部分。

## 3. 应用判定

**何时使用**：
- 设计 writer prompt、executor prompt、review prompt
- 多 Agent 或多层 orchestration 的任务
- 需要 persona、规则、workflow、包装工件共同参与的任务
- 当 prompt 已经足够长，且输出开始出现 meta 腔、复述感、判断力下降时

**如何实践**：
1. 先把候选 prompt 里的每一句话标成 `control-plane` 或 `task-plane`
2. 删除所有不会直接改善下游输出的 `control-plane` 句子
3. 保留真正影响结果的句子：任务目标、事实边界、允许证据、风格约束、判断要求、输出格式
4. 重新检查：如果某个约束已经由调用方或输入工件保证，就不要再写进下游 prompt

## 4. 反面案例

- 告诉 writer 它是 `Hoveath-compatible`。这属于 persona 来源说明，不是写作任务本身。
- 告诉 writer 不要混账号，但调用方已经只给了一个账号 package。这个边界已经由上游保证。
- 在 task prompt 里解释系统为什么这样组装，而不是直接告诉它要写什么。

## 5. 正面模式

- 告诉 writer：事实边界在哪里
- 告诉 writer：哪些判断必须给
- 告诉 writer：什么风格允许，什么腔调禁止
- 告诉 writer：输出结构是什么
- 把其余系统信息留在上游

## 6. 相关公理

- **A08 提示质量是主要杠杆**：提示质量不只取决于是否清晰，也取决于是否分层干净。
- **A03 从 IC 到管理者的心智转变**：管理者的工作之一，就是决定下游该知道什么，不该知道什么。
- **T03 上下文隔离**：prompt 层也需要信息域隔离，不能把不同层级的语义混在一起。

## 7. 简化准则

在交付 prompt 前，最后问一次：

`这句话是在帮助下游把事做好，还是只是在解释我们怎么准备它。`

如果答案是后者，就删掉。
