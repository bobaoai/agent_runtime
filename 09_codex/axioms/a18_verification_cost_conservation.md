# A18. 验证成本守恒

## 1. 核心公理

代理工具的验证成本，等于它声称要消灭的那种专长。让非专家用户验证 LLM 生成的 SQL、代码、合同条款、数据报表或医学建议，需要的正是被代理掉的那种专家能力本身。这意味着"AI 让非专家也能做专家的事"这个承诺在没有可验证接口时是结构性虚假的：要么用户已经具备验证能力（那他不是真正的非专家），要么他没有（那他就是在赌 LLM 没出错）。

## 2. 深度推演

### 2.1 验证不是输出本身的属性，是用户能力的属性

一个 LLM 生成的 SQL 可以语法正确、执行无错、返回看起来合理的数字，但用户能不能判断它是否回答了真正的问题，取决于用户能不能读懂这段 SQL 并理解它的语义。Text-to-SQL 工具卖的是"不用懂 SQL 也能查数据"，但要知道答案对不对，恰好需要懂 SQL。这条逻辑可以平移到任何 agent 代理专家工作的场景。

### 2.2 "看起来合理"不等于"能被验证"

验证成本守恒的隐性破坏力在于：错误经常是 plausible 的（数字在量级内、语气得当、逻辑自洽）。非专家用户在面对 plausible 输出时会默认通过，而不会主动质疑。这导致系统在外观上是可用的，在语义上持续失准。Plausibility 是 verifiability 的伪装，必须用工程手段拆开它们。

### 2.3 守恒律不能被绕过，但可以被转移

"验证成本守恒"不意味着 agent 工具没有价值，而意味着验证成本无法消失，只能被转移到三个地方：
1. **转移到产物结构上**：让产出对应到"已治理的定义"（semantic layer、governed metric、code review 通过的接口、API contract），用户验证的不再是原始 LLM 输出，而是它命中了哪个已知正确的对象。
2. **转移到二次系统上**：用确定性代码 / 第二个独立 agent / 自动化测试去验证第一个 agent 的输出（generate-and-critique loop、A/B 校验、sqlglot 校验、数据 golden set 对比）。
3. **转移到人在回路里的少数关键节点**：保留人工验证，但只在高风险或异常触发时介入，配合可读的 diff / dry-run / 摘要。

不做任何转移就直接给非专家暴露原始 LLM 输出，等于把验证成本伪装成不存在。

### 2.4 这条守恒律说明了 semantic layer 的真实价值

为什么 Omni / dbt / Cube 反复强调 AI 必须跑在 semantic layer 上、而不是直接对原始 schema 生成 SQL？因为 semantic layer 把验证成本从"用户读 SQL"转移到了"建模者治理定义"。后者是一次性投入、可复用、由真正的专家完成。AI agent 不再创造新的验证负担，只是把已被治理的定义投影成自然语言响应。同样的逻辑在 coding agent 里对应"生成代码必须落在已审核过的库 / 接口 / 模式上"，在 ops agent 里对应"动作必须命中已批准的 runbook"。

### 2.5 它和 V02 的关系

V02 说"信任来自可验证性，必须为系统设计验证接口"。A18 说"验证接口的成本不会因为换上 AI 就消失，它只能被转移"。V02 是设计 imperative，A18 是经济判断。两条合在一起意味着：评估一个 agent 产品时，先问"验证成本被转移到了哪里"，如果答案是"用户自己用专家眼光看一眼"，这个产品就还没解决可靠性问题。

## 3. 应用判定

### 何时使用

- 评估一个 agent 产品 / 内部工具 / agent workflow 时
- 听到"AI 让非专家也能做 X"的承诺时
- 设计自家 agent 工作流暴露给非技术同事时
- 看到 LLM 输出 plausible 但你怀疑它在某处错了时
- 决定要不要在某个流程中引入 agent 时

### 如何实践

1. 先问：这个产物的"对/错"判定，需要哪种专长？
2. 再问：当前用户群体里，谁具备这种专长？比例多少？
3. 如果用户不具备：验证成本被转移到哪里了？产物结构？二次系统？人在回路？
4. 如果三个都没有，要么补一个，要么把目标用户群改成具备验证能力的群体，要么明确这是"赌一把"产品并相应限制使用面。
5. 不要相信"模型够强就不需要验证"——这是验证成本守恒的常见伪装话术。

## 4. 相关公理

- **V02 可验证性是信任的地基**：V02 给出 imperative，A18 给出守恒律。
- **A04 可靠性是管理问题**：可靠性管理三角的"验证"维度对应 A18。
- **V05 信任归因双维度**：A18 说明为什么"信任域"必须独立于"信任主体"被定义。
- **A12 AI 原生开发范式**：semantic layer / governed interface 是验证成本转移的标准范式。
- **T10 Index 优先，AI 填补语义缺口**：让 AI 跑在结构化事实之上，本质是把验证成本前移到 index 构建阶段。

## 5. 简化准则

评估任何 agent 产品或工作流前，至少问三件事：

1. 这个产物的"对/错"由谁来判定？
2. 那个判定者，需要的专长和被代理掉的专长是不是同一个？
3. 如果是，验证成本被转移到哪里了？还是默认让用户赌一把？
